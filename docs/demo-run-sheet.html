The schema as a category

Your day-one graph used entity objects and relationship arrows. The instructor's sample uses the stricter functorial reading — objects are types (entities, attributes, and finite enums), and every column is a morphism. Re-read in that notation, the shipped schema differs from your graph in three places, and each difference is a real finding.

Every foreign key, as an arrow

menu_items —category→ categories totalRESTRICT A dish must sit in a course. You cannot delete a course out from under its dishes.

Finding 1 — Role is two objects, not one

Your graph has a single Role box receiving both User —hasRole→ and Shift —requiresRole→. The schema says otherwise: 

users.role           CHECK (role IN ('customer','staff','manager','admin'))
shift_templates.role CHECK (role IN ('server','host','cleaner','cook'))

Two disjoint finite sets, so two distinct objects. Drawing one box was a type error — it would let you compose an arrow that says a shift requires a manager, which is a different kind of thing from requiring a cook. The code keeps them apart too: routes/users.js:9 and schedule/store.js:3, each with a "mirrors" comment.

This is also the answer to "why is there no roles table?" — in this notation a finite enum is already an object. A physical table would add a join and buy nothing, because the element set is fixed by the application, not by data.

Finding 2 — the availability arrow pointed the wrong way

Your graph draws Staff —hasAvailability→ Availability. But a person has many availability windows, so that assignment is not a function and cannot be an arrow. The FK is the other direction: 

staff_availability.user_id → users            -- Availability —user→ Staff

In the functorial model arrows are total functions, so a foreign key can only ever point from the many side to the one side. "Has many" is not an arrow — it is the preimage of one.

Finding 3 — Image stopped being an object

Your graph has MenuItem —hasImage→ Image. There is no images table. What shipped is menu_items.image_path TEXT — nullable — with the bytes on a separate Docker volume served by /api/images.

So the arrow lands in 1 + String, and the image itself lives outside this category entirely. The database stores a name, not the thing. Worth saying out loud: that is a boundary, and it is why the database and the uploads are two volumes that can get out of step — which is exactly why db/attach-photos.js is a separate command from seed.js.

Finding 4 — a square that should commute, and doesn't

A notification carries both a user and a shift. An assignment carries both a user and a shift. Nothing makes them agree: the schema happily stores a notification telling a cleaner about a shift they are not on.

SQLite cannot state "these two paths agree", so the application maintains it — notifyAssignees() in backend/schedule/store.js walks the assignments and writes one notification each. The category can express an invariant the database cannot enforce. That is a good thing to be able to name.

Finding 5 — the analytics queries are composition

"Views per course" is the composite menu_item_views —item→ menu_items —category→ categories. The SQL is that composite, spelled out as a join chain — viewsByCategory() in backend/analytics/queries.js. Nothing clever, but it is a clean example of a path in the schema category becoming a query.

Partial morphisms — and why one of them drives an algorithm

Four columns are nullable, so four arrows are partial: they land in 1 + X. Usually that is just "unknown". One of them is load-bearing. 

menu_items.cost_cents  INTEGER  CHECK (cost_cents IS NULL OR cost_cents >= 0)
-- "an item whose cost nobody has entered yet is excluded from margin
--  reporting rather than being reported as 100% profit"   — schema.sql:36

The gacha weights every dish by margin. Margin is price − cost, so it is only defined where cost_cents is. But the draw has to be a total function on the pool — every available dish needs a weight. So the algorithm must decide what to do on the 1 component, and there are exactly three options:

OptionCategoricallyWhy not / why
Exclude the dish Restrict the domain The machine would silently hold fewer dishes than the menu shows. A data-entry gap in the office would edit the dining room.
Treat cost as 0 Extend with a wrong value Reports it as pure profit — the exact thing the schema comment refuses to do. It would make that dish the most promoted on the board.
Score at the median of the defined part Extend with the best available estimate Chosen. "As promoted as a typical dish on this menu" — as far as honesty goes when nobody has entered a number. menu/gacha.js:136
say "The nullable column isn't a modelling accident I worked around — it's a partial function, and the feature had to pick a total extension of it. The verification script prints which dishes are riding on that estimate, so the fix is obvious: enter the cost."

Two more structuring decisions worth having ready

Specials: attributes instead of an object

v1 of this project had a separate specials table — Special —item→ MenuItem, many over time. This version put them on the item as four columns plus CHECK (special_price_cents IS NULL OR discount_percent IS NULL).

The trade, stated plainly: collapsing the object loses the history — the schema can only hold the current special, never past ones. It also needs a table-level CHECK to say "exactly one of these two", because SQL has no sum type; in the category that codomain is a coproduct and would need no constraint at all.

Templates and shifts are two objects, on purpose

shift_templates is a weekly rule — day_of_week ∈ {1..7} plus two HH:MM strings. shifts is an instance, with absolute timestamps. Same-looking data, different objects, because they answer different questions.

The payoff is concrete: a 22:00–02:00 closing shift is one unambiguous interval, so the overlap test is a.start < b.end AND b.start < a.end with no midnight special case (schedule/store.js). And UNIQUE(template_id, shift_date) is what makes "generate this week" idempotent — you can press it twice.

Questions you should expect

"Why SQLite?"

Single file on a Docker volume, so the whole environment is docker compose up. better-sqlite3 is synchronous, which keeps the route handlers readable. Concurrency wasn't the assignment — and the schema is ordinary SQL, so Postgres is a migration, not a rewrite.

"Could someone forge a role in the JWT?"

They'd have to forge an HS256 signature. But even if they did, it wouldn't help — middleware/auth.js re-reads the role from the database on every request and the token's copy is only used to find the row.

"What about SQL injection?"

Every query is a prepared statement with named parameters. The one place user input touches SQL structure is the sort order, and that's a whitelist lookup — SORTS[sort] || default in routes/menuItems.js, so an unknown value falls back rather than interpolating. Search also escapes % and _ so a search for "100%" doesn't match everything.

"Why no roles table?"

Finding 1 above. A four-element fixed set is already an object in the category; a table would add a join and no information. The trade is real though: adding a role means a schema change, not a row.

"Where are the tests?"

Don't dodge this. There is no test framework — that's the biggest gap. What exists instead: npm run gacha-weights asserts the feature's actual claim and exits non-zero, and the standup log records bugs found by driving the UI rather than reading it. Next step would be supertest against the routes, starting with the permission matrix, since that's the part where a regression is a security bug.

"Is the gacha just random?"

No — and the code never uses the word. Each dish gets a weight from margin and from how overlooked it is, both normalised across the pool, blended and squared. Roulette-wheel selection over the cumulative weights. Every dish keeps a floor of 0.15 so the machine can still surprise you.

"Why is the view count a good demand signal?"

It isn't a great one — it's the best one available, because there's no orders table. Say that plainly. A view is recorded when someone opens a single dish, never when a dish merely appears in the grid, which is the closest this app gets to intent.

"What would you do differently?"

staff_availability has full CRUD and no UI, and — worse — the scheduler never consults it. The arrow exists and the composition is never taken. That's the first thing I'd finish, because it's the one place where the model promises something the app doesn't do.
