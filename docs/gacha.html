How the dish gacha works

Turn the dial, get one dish. The draw is weighted toward dishes that are both profitable and overlooked — so it is a merchandising tool wearing a capsule machine. Every number on this page is real, from npm run gacha-weights against the seeded menu.

the shape of it

One request, four stages

1 · pool

Every available dish, plus its view count over the last 30 days.

→

2 · score

Two numbers per dish: how profitable, how overlooked. Blended into one weight.

→

3 · draw

Pick one, with probability proportional to its weight.

→

4 · strip

Rebuild the response from a named field list. Cost and scores stay behind.

Stage 1 is the only SQL. Stages 2 and 3 are pure arithmetic in backend/menu/gacha.js — no database, which is why the whole thing can be re-run offline by the verification script.

stage 2a

Signal one — margin

What the shop actually banks on a plate: the price the customer pays minus the cost. In cents, not percent, because rent is paid in cents — Sukiyaki is only a 34% margin but earns 950¢ a serving, more than anything else on the board.

It uses the effective price, so Curry Udon counts at $9.99 (26% off) rather than its $13.50 list. Otherwise the machine would push discounted dishes hardest — backwards, since a special is already a promotion. That is why it ends up last.

Scaled across the pool: best margin = 1.00, worst = 0.00.

stage 2b

Signal two — how overlooked

Views over 30 days, inverted and log-damped: 1 / log₂(views + 2). The + 2 is what makes a dish with zero views score exactly 1.00 without any special case — and the log stops one runaway dish from flattening everything else into noise.

Curry Rice is the most-viewed dish on the menu, so it scores 0.00 here — the least overlooked thing there is.

stage 2c · the core idea

The map

Put both scores on one chart. Profitable to the right, overlooked upward — so the dishes worth promoting are in the top-right. The shading is the weight each position earns.

← low marginmargin scorehigh margin →

The pale diagonals are lines of equal weight. They run at 45° because the two signals are simply averaged — so a point can trade margin for obscurity one-for-one and land on the same line.

But look at the spacing: the bands crowd together toward the top-right. That crowding is the whole trick, and it comes from squaring the average.

stage 2d

Why it is squared

Average the two scores and you get quality. A dish can reach 0.5 by being perfect on one axis and worst on the other — which is not what we want to promote. Squaring bends the curve so the middle is punished harder than the top:

Sukiyaki has the best margin on the whole menu, but it is the second-most-viewed dish. Tofu Udon is merely good at both. On a plain average Sukiyaki is only 10% behind — after squaring it is 23% behind. One exponent buys the word “and”.

The curve also never reaches zero: it starts at 0.15. That floor is what keeps every dish drawable — without it the worst dish would be impossible, and the machine would stop being a gacha and start being a vending machine.

stage 3

The draw

Lay every weight end to end and pick a point at random along the whole strip. Whichever segment you land in is the dish. Wider segment, likelier dish — that is the entire selection algorithm.

If every dish were equally likely each segment would be 12.5% wide. Compare: the three quiet, profitable dishes take 53% between them, while Curry Rice — second-best margin, but the most-viewed dish on the menu — is pushed down to 9.7%.

stage 4

What leaves the server

All that reasoning is the shop's business. The response is rebuilt from an explicit list of fields rather than by copying the row, because the only reliable place to stop a column is before it leaves.

Goes to the browser

  • name, description
  • price_cents
  • effective_price_cents
  • category_name
  • image_path
  • pool_size

Never leaves the process

  • cost_cents
  • views
  • margin_cents
  • margin_score
  • overlooked_score
  • quality, weight

The client is told which dish came out, and nothing about why. There is no ?seed= parameter either — a caller who could replay draws could read the margin ranking of the menu straight off the machine.

the reason it keeps working

A draw is not a view

If turning the dial counted as a view, the machine would promote a quiet dish, count its own promotion as interest, and demote it again — with nobody having looked at anything. The counter would be measuring the machine instead of the room.

So the draw is a read with Cache-Control: no-store and no write at all. The view is recorded only when someone clicks See dish, through the same endpoint the menu already uses. You can check it: run npm run inspect-db, draw ten times, run it again — the count is unchanged. Click through once and it goes up by exactly one.

the awkward case

One dish has no cost recorded

Sesame Sauce Salad has no cost_cents, so its margin cannot be computed — but the draw still has to give it a weight. Three options, and only one is honest:

OptionWhat happensVerdict
Leave it out The machine holds 7 dishes while the menu shows 8 A blank field in the office would quietly edit the dining room
Call the cost zero Scores as pure profit — the best dish on the board Promoted hardest for the worst reason
Score it at the median Treated as a typical dish on this menu Chosen — as far as honesty goes when nobody has typed the number in

The median here is 0.265, which happens to land exactly on Sardine Ochazuke — which is why the two share a point on the map above. The verification script prints which dishes are running on this estimate, so the fix is obvious: enter the cost.

proving it

The claim is tested, not asserted

There is no test framework in this project. Instead the feature's claim is made falsifiable — npm run gacha-weights prints the table above, then draws 100,000 times through the real selector and compares what came out against what was predicted. Then it splits the menu at both medians and checks the claim directly: 

CLAIM  high-margin half draws 1.96x as often as its opposite   OK
CLAIM  overlooked half draws 1.65x as often as its opposite    OK
max |Δ| = 0.12pp over 100,000 draws

It exits non-zero if either ratio falls to 1. A green run is a real check, not a printout.
